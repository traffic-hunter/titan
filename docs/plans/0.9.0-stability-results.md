- 코드 기준: `a3d5f96b` + PR 1 측정 도구 변경(미커밋)
- 상위 문서: [0.9.0 안정화 계획](0.9.0-stability-plan.md), [0.9.0 안정화 구현 설계](0.9.0-stability-design.md)

## 2. 실행하지 않은 것

- 조합별 3회 반복, 5만 건 전체 행렬, 프로듀서 8·16, 256B·16KiB payload.
- 30분 지속 부하, 과부하 fixture, 느린 수신자 실험.
- direct 경로 비교 실행. fixture는 `--path direct`를 지원하지만 이번에는 dispatch만 측정했다.
- 고정 스레드(`--dispatch-mode platform`) 서버 측정. 통합 테스트에서만 사용했다.

이 항목들은 PR 6의 출시 검증에서 수행한다.

## 3. receipt 모드 — 정상 부하

수락 RECEIPT를 기다리는 모드다. 프로듀서당 in-flight는 1건이다.

| transport | 메시지 | 프로듀서 | 수락 | 수신 | 중복·불명·미전송 | 경과 | 처리량 | 전달 p50/p95/p99 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: | --- |
| tcp | 10,000 | 1 | 10,000 | 10,000 | 0 | 0.708s | 14,115/s | 0.074 / 0.112 / 0.155 ms |
| tcp | 10,000 | 4 | 10,000 | 10,000 | 0 | 0.460s | 21,757/s | 0.202 / 0.348 / 1.500 ms |
| tcp | 100,000 | 1 | 100,000 | 100,000 | 0 | 4.224s | 23,672/s | 0.041 / 0.053 / 0.063 ms |
| tcp | 100,000 | 4 | 100,000 | 100,000 | 0 | 2.617s | 38,207/s | 0.101 / 0.222 / 0.867 ms |
| websocket | 10,000 | 1 | 10,000 | 10,000 | 0 | 0.782s | 12,781/s | 0.078 / 0.130 / 0.197 ms |
| websocket | 100,000 | 4 | 100,000 | 100,000 | 0 | 2.787s | 35,886/s | 0.105 / 0.255 / 0.894 ms |

전 실행에서 rejected·unknown·localNotSent·duplicates·contradiction·미시도가 모두 0이고 집계 합이 맞았다.
**receipt 모드에서는 10만 건에서도 유실이 재현되지 않았다.**

## 4. write 모드 — deadline 내 미수신 재현

로컬 쓰기 접수만 확인하는 모드다. 수락 응답을 기다리지 않으므로 발행이 제한되지 않는다.

| transport | 메시지 | 프로듀서 | 쓰기 접수 | 수신 | 미수신 | 경과 | 판정 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | --- |
| tcp | 10,000 | 1 | 10,000 | 10,000 | 0 | 0.315s | 통과 |
| tcp | 10,000 | 4 | 10,000 | 6,312 | 3,688 (36.9%) | 120.0s | deadline 초과 |
| tcp | 50,000 | 4 | 50,000 | 41,786 | 8,214 (16.4%) | 120.0s | deadline 초과 |
| tcp | 100,000 | 4 | 100,000 | 10,846 | 89,154 (89.2%) | 120.0s | deadline 초과 |
| websocket | 10,000 | 4 | 10,000 | 8,156 | 1,844 (18.4%) | 120.0s | deadline 초과 |

미수신이 발생한 실행에서도 localNotSent·unknown·rejected 집계는 모두 0이었다. 이는 로컬 쓰기 접수가
모두 성공했다는 뜻이다. write 모드는 서버 수락을 관측하지 않고 현재 runner는 개별 ERROR를 요청 ID에
연결하지 않으므로, rejected=0만으로 서버 거부가 전혀 없었다고 판단할 수 없다.

표의 미수신은 **120초 관측 종료 시점까지 도착하지 않은 고유 ID 수**다. 이 결과만으로 영구 유실이나
정확한 손실 지점을 확정하지 않는다. 압력에 따른 exporter 건너뛰기가 코드상 후보이며, PR 2·3에서
서버의 큐 잔량·전달 실패·skip 지표와 대조해야 한다.

미수신 비율은 단일 실행마다 달랐다. 메시지 수에 따른 인과관계나 정확한 발행률 경계는 반복 실행과
서버 측 지표를 확보한 뒤 판단한다.

### 4.1 계획 문서의 증상과의 관계

계획 문서의 관측 증상은 "1만은 정상, 10만부터 수신 누락·타임아웃"이었다. 이번 조건에서는
프로듀서 1개의 write 모드 1만 건은 통과했고, 프로듀서 4개의 write 모드는 1만 건에서도 미수신이
발생했다. 반면 receipt 모드는 프로듀서당 한 건의 수락 응답을 기다리며 10만 건도 통과했다.
따라서 총 메시지 수 외에 발행 속도·동시성이 영향을 주는지 추가 검증해야 한다. write 모드도 로컬 쓰기
접수를 한 건씩 기다리지만 서버 수락까지 기다리지는 않는다는 차이가 있다.

## 5. 최초 측정자가 기록한 별도 결함

아래 두 가지는 최초 측정자가 남긴 코드 관찰과 재현 기록이며 PR 1 범위에서 고치지 않았다.
PR 게시 검토에서는 해당 별도 재현을 다시 실행하지 않았다. 후속 작업에서 명세와 재현 증거를 확인한다.

### 5.1 헤더 값의 콜론이 왕복하지 않는다

서버는 나가는 프레임의 헤더 값에서 `:`를 STOMP 1.2 규칙대로 `\c`로 escape하지만, 들어오는 프레임을
읽는 `StompChannelDecoder.StompParser.parse`는 unescape하지 않는다. 따라서 `receipt:aa:bb`로 보낸
SUBSCRIBE에 대해 서버는 `receipt-id:aa\cbb`를 돌려주고, 클라이언트의 receipt 대기는 영원히 매칭되지
않는다.

재현: 원시 소켓으로 `SUBSCRIBE ... receipt:aa:bb:cc` 전송 → 응답 `RECEIPT receipt-id:aa\cbb\ccc`.

영향: 콜론·역슬래시·개행을 포함한 모든 헤더 값. runner는 receipt ID를 `-`로 연결해 이 결함을 피한다.

### 5.2 클라이언트 heartbeat 협상이 설정값을 무시한다

`DefaultStompClientHandlers.DefaultConnectedHandler`는 협상에 클라이언트의 실제 설정 대신
`StompFrame.HeartBeat.DEFAULT`를 사용한다. `StompSessionOption`에 `heartbeatX(0)`, `heartbeatY(0)`을
주고 CONNECT에 `heart-beat:0,0`을 보내도 서버의 `1000,1000`이 그대로 적용된다. 그 결과 클라이언트는
**수신 프레임이 2초 이상 없으면 스스로 연결을 끊는다.** `lastActivatedAt`은 수신에서만 갱신되므로
발행만 하는 연결이 대상이다.

재현: 연결 후 20ms 간격으로 send만 수행 → 83건(약 1.7초) 뒤 연결이 끊기고 이후 요청이
`ClientException: STOMP client is not connected`로 실패한다.

영향: write 모드의 저속·장시간 실행. 위 부하 결과와의 관련 여부는 연결 로그와 함께 확인해야 한다.
PR 6의 30분 지속 부하 전 별도 재현·수정이 필요하다.

## 6. 도구가 이번에 확보한 것

- 단계 분리: 요청 / 시도 / 쓰기 접수 / 수락 / 수신 / 중복 / 명시적 거부 / 미전송 확인 / 결과 불명 / 미시도.
- 관측할 수 없는 단계는 null로 보고한다. `written`은 항상 null이다. 현재 채널 promise는 일부 write가
  남아도 성공하므로 socket write 완료를 알 수 없다.
- 공통 deadline과 freeze. 보고서를 고정한 뒤 도착한 이벤트는 수치를 바꾸지 않고 별도로 센다.
- 구독 RECEIPT 이후에 발행을 시작한다.
- 실행 manifest에 옵션·커밋·fixture의 해석된 설정·환경을 함께 남긴다.
- 지연 누락을 0으로 채우지 않는다. 표본이 없는 단계는 분포 자체가 없다.

## 7. 다음 단계

- 5.2는 PR 6 이전에 별건으로 처리한다. 그대로 두면 지속 부하 측정이 불가능하다.

## 8. PR 게시 전 검토

- 위 11개 실행의 requested·accepted·received·elapsed 값이 로컬 원시 manifest와 일치하는지 확인했다. 원시 로그는 이 PR에 포함하지 않는다.
- 시작·연결 실패한 producer도 종료 대상에 포함하도록 수정했다.
- producer 종료 유예시간 내 종료됐다는 이유로 원래 deadline을 충족한 것으로 바뀌지 않도록 판정을 분리했다.
- 전송 시점이 불명확한 일반 예외는 localNotSent로 추정하지 않고 unknown으로 분류했다.
- receipt 모드에서 accepted가 누락된 결과는 CLI에서 성공으로 처리하지 않도록 수정했다.
- 이 검토는 기준 부하의 재실행이 아니다. 위 수치는 검토 수정 전 실행 결과다.
