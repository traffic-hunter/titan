# Titan 0.9.0 안정화 구현 설계

- 작성일: 2026-09-13
- 코드 기준: `a3d5f96b` 및 현재 main의 관련 구현
- 상위 계획: [0.9.0 안정화 계획](0.9.0-stability-plan.md)
- 상태: 구현 전 설계. 아래 새 타입과 API는 제안 계약이며 현재 존재하는 API가 아니다.
- 목표: 정상 연결의 dispatch 큐 경로에서 수락 메시지를 압력 때문에 버리지 않고, 한도 초과 요청을 명시적으로 거부한다. TCP·WebSocket에 같은 계약을 적용한다.

## 1. 추가 조사 결과와 설계 원칙

### 1.1 쓰기 완료는 현재 API의 성공과 다르다

`ChannelTasks.writeAndFlush()`는 outbound pipeline 실행과 flush 시도가 반환되면 promise를 성공시킨다. `NewIONetChannel.Internal.flush()`는 socket write가 0이면 나머지 데이터를 ChannelWriteBuffer에 남긴다. 따라서 현재 send 성공을 모든 바이트의 소켓 쓰기 완료로 집계하면 안 된다.

- 기존 성공 단계는 측정에서 `writeSubmitted`로 부른다.
- 전송 byte가 실제 socket에 모두 인계됐을 때 별도의 `written`을 기록한다. 이는 상대 애플리케이션 수신·처리 완료를 뜻하지 않는다.
- `accepted`는 SEND의 RECEIPT, `received`는 테스트 수신 핸들러가 확인한 ID로 집계한다.
- PR 1의 기준 서버에서는 지원하지 않는 단계에 null/미지원 표시를 사용한다. RECEIPT 성공을 근거로 written 시각이나 개별 쓰기 지연을 만들어내지 않는다.

### 1.2 기존 pressure 설정은 실제로 비활성일 수 있다

`StompServerFanoutLauncher`는 최상위 flow-control과 queue.enabled가 모두 true일 때만 큐 byte 한도를 적용한다. 현재 titan-env.yml의 최상위 flow-control.enabled는 false다. 설정 파일의 64MiB 숫자만 보고 실제 제한이 적용됐다고 판단하지 않는다.

- 테스트는 해석된 런타임 설정을 저장하고, 큐 MBean의 실제 max/resume 값과 대조한다.
- 안정화 구현에서는 큐 byte 한도와 admission 상한을 안전 한도로 취급해 항상 적용한다. 선택적인 heap damper의 활성화와 분리한다.
- 기본 큐 한도는 64MiB, resume는 48MiB로 통일한다. Long.MAX_VALUE를 사용하는 무제한 기본값은 제거한다. 기존 실제 설정과 수정 후 기본값을 각각 기록해 동작 변경을 숨기지 않는다.

### 1.3 기본 원칙

- 수신자별 backlog를 추가하지 않는다. 큐에 한 개의 in-flight 메시지를 두고 대상별 진행 상태만 추적한다.
- I/O 이벤트 루프에서 기다리거나 네트워크 대기 동안 잠금을 잡지 않는다.
- 수락한 메시지의 최종 결과는 전달 완료 또는 사유가 있는 종료다. full/writable pressure는 수락 메시지의 종료 사유가 아니다.
- 운영자의 purge·강제 삭제와 수신 연결 종료는 명시적 보존 예외다. 미전달 건수를 기록한다.
- 자동 재전송은 전송 전 거부로 확인된 경우에만 허용한다. 부분 쓰기 실패는 UNKNOWN이며 프레임 전체를 다시 보내지 않는다.

## 2. PR 1 — 재현·측정 계약

### 2.1 runner 설정

기존 PerfTestOptions와 Go Config에 다음을 추가한다.

| 설정 | 값·기본값 | 의미 |
| --- | --- | --- |
| transport | tcp / websocket, 기본 tcp | 실제 연결 방식 |
| websocket-path | 기본 /stomp | WebSocket일 때 사용 |
| send-mode | receipt / write, 기본 receipt | 수락 측정 / 기존 발행 속도 비교 |
| path-label | dispatch / direct, 기본 dispatch | 실행 대상 경로 표기; 서버 fixture 설정과 일치 여부 확인 |
| completion-timeout | 기본 120초 | 워밍업 이후 전체 측정 deadline |

프로듀서당 동시 SEND 수는 기존처럼 1개로 고정한다. receipt 모드는 응답까지 기다리므로 write 모드와 처리량을 별도로 비교한다. 한 모드의 성공으로 다른 모드의 안정성을 대체하지 않는다. 각 프로듀서는 자동 재시도를 사용하지 않는다.

### 2.2 메시지·receipt 식별

- payload: `runId(long), producerId(int), sequence(int), sentAtNanos(long), padding`의 24바이트 측정 헤더를 사용한다. payloadBytes는 헤더를 포함한 전체 길이다.
- sequence는 전체 요청에서 고유한 0..N-1 값이다. 워밍업은 별도 단계 식별과 순번으로 추적한다. 모든 워밍업에 같은 ID를 사용하지 않는다.
- receipt ID는 실행·프로듀서·sequence를 조합한다. SUBSCRIBE는 별도 receipt ID를 사용하며 RECEIPT 확인 후 발행 준비 완료로 처리한다.
- 수신 핸들러는 실행 ID·길이·sequence를 검사하고 다른 실행의 메시지와 malformed 메시지를 별도 집계한다.

### 2.3 MeasurementLedger

ID별 상태를 담당하는 `MeasurementLedger`와 읽기 전용 `MeasurementSnapshot`을 추가한다. 각 ID의 갱신은 짧은 동기화 또는 원자적 상태 전이로 보호하고, 네트워크 작업은 수행하지 않는다.

단계는 독립적으로 저장한다. RECEIPT보다 MESSAGE가 먼저 관측될 수 있으므로 단일 순차 enum으로 received를 accepted 뒤에 강제하지 않는다.

| 결과 필드 | 정의 |
| --- | --- |
| requested / attempted / notAttempted | 전체 계획 / 호출 시도 / 미시도 |
| writeSubmitted / written | 로컬 쓰기 작업 접수 / 실제 전체 socket write 완료; 단계 미지원은 null |
| accepted | receipt 모드에서 수락 RECEIPT가 확인된 고유 ID 수; write 모드는 null |
| rejected | 해당 ID가 수락되지 않았음을 서버가 명시적으로 응답 |
| localNotSent | 호출 시도는 했지만 전송 전에 거부된 것으로 확인 |
| unknown | receipt 모드에서 accepted/rejected/localNotSent 어느 쪽도 확정되지 않은 시도 |
| received / duplicates | 고유 수신 ID 수 / 추가 수신 횟수 |
| acceptedNotReceived | 수락은 확인됐지만 deadline까지 수신하지 못한 ID 수 |
| contradiction | rejected/localNotSent인데 수신되는 등 계약상 모순 |

receipt 모드에서 `attempted = accepted + rejected + localNotSent + unknown`, `requested = attempted + notAttempted`를 검증한다. received는 별도 관측 집합이므로 이 합계에 더하지 않는다. write 모드는 accepted/unknown 기반 수락 판정을 하지 않고 end-to-end 수신과 미수신을 보고한다.

### 2.4 완료·실패 처리

1. 연결·구독·워밍업 완료 후 공통 시작 barrier를 연다.
2. 모든 SEND 대기는 동일한 monotonic deadline의 남은 시간을 사용한다.
3. 전송 오류는 ID별로 기록한다. 하나의 connection 종료가 그 연결의 모든 미완료 요청을 명시적 거부로 바꾸지는 않는다.
4. deadline 도달 시 신규 전송을 중지하고 runner executor를 중단·join한다. 결과 snapshot을 고정한 후 연결을 정리한다.
5. 수신 callback도 ledger의 freeze와 동일한 조율을 사용한다. freeze 이후 이벤트는 확정 보고서를 변경하지 않는다.
6. 연결 종료·종료 대기 실패는 별도 cleanup 결과로 남긴다. 미완료 스레드를 남긴 실행은 성공 처리하지 않는다.

지연은 유효 고유 수신의 end-to-end latency와 RECEIPT latency를 각각 p50/p95/p99/max로 집계한다. timeout은 누락 샘플을 0으로 채우지 않는다. 기존 failed 하나로 여러 원인을 합쳐 성공 여부를 판단하는 경로를 제거한다.

### 2.5 기준 실행과 산출물

- 서버 fixture와 runner를 별도 JVM으로 실행한다. fixture는 direct/dispatch, fixed/virtual, TCP/WebSocket과 한도를 명시적으로 선택하고 동적 포트·해석된 설정을 출력한다.
- 부하 전에 구독 RECEIPT 및 실제 큐 한도 확인을 마친다. 실행마다 별도 group/destination 또는 깨끗한 fixture를 사용한다.
- 실행 manifest에는 서버/runner 커밋, JDK·OS·CPU·메모리, JVM 인자, 설정 사본, 실제 옵션, 반복 번호와 시작 시간을 남긴다.
- 원시 결과는 `build/stability/<run-id>/`에 JSON·로그·지표로 저장하고 요약과 필요한 증거만 결과 문서에 반영한다.
- PR 1은 서버 전달 정책을 바꾸지 않는다. 현재 오류가 receipt ID를 포함하지 않으면 추정해 rejected로 만들지 않고 unknown으로 남긴다.

## 3. PR 2 — 비동기 결과와 소유권

### 3.1 export 완료 계약

AggregationResult를 삭제하고 `DispatchExporter.export(...)`가 완료 신호만 반환한다. DispatchDelivery나 DeliveryReport 같은 새 타입도 만들지 않는다.

구현 시점의 코드를 확인한 결과 AggregationResult를 **읽는 호출자가 없었다.** exporter 세 개와 벤치마크가 생성만 하고, FanoutDispatchChainHandler는 반환값을 버린다. 그러면서 StompDispatchExporter는 send promise listener에서 `succeeded++`를 호출했는데, 구독이 서로 다른 연결에 있으면 각 연결의 이벤트 루프가 같은 int 필드를 경합한다. 동시성 보호를 덧붙이는 대신 타입을 제거한다.

```java
CompletionStage<@Nullable Void> export(String group, Destination destination, Buffer payload);
```

- stage는 이 export가 시작한 모든 쓰기가 끝나면 완료된다. 결과 값을 싣지 않는다.
- 실패한 쓰기도 완료로 센다. stage는 예외로 완료되지 않는다. `CompletableFuture.allOf`는 입력 하나가 실패하면 전체를 예외로 완료하므로 target마다 `handle`로 눌러야 한다.
- 쓸 수 없는 구독자는 건너뛰고 기다리지 않는다. skip 사실은 SlowConsumerMetrics에 남는다.
- target이 0이면 stage는 이미 완료 상태다. `allOf()`가 빈 입력에 완료된 future를 돌려준다. targets=0을 성공 전달 1건으로 세지 않는다는 규칙은 그대로이며, PR 3의 큐 경로가 대상 없음 상태에서 메시지를 유지한다.
- 완료 스레드는 고정되지 않는다. 마지막 쓰기를 끝낸 연결의 이벤트 루프일 수 있으므로 dependent에서 블로킹하지 않는다. 게이트웨이 executor로 넘기는 것도 답이 아니다. 현재 consumer 루프가 그 풀의 스레드를 하나씩 영구 점유하기 때문이다.
- cancel과 대상별 결과는 PR 2에 넣지 않는다. 취소 호출자는 PR 3 §4.6에서, written·cancelled·failedNotSent·unknown 구분은 PR 5 §5의 큐 지표에서 처음 필요해진다.
- target 식별에 물리 연결과 구독 인스턴스를 포함하는 문제는 대상별 결과를 도입할 때 함께 정한다. 값을 싣지 않는 stage에는 식별자가 필요 없다.

### 3.2 비동기 payload 수명

- Buffer 인자의 유효 범위를 호출 중에서 stage 완료까지로 넓힌다. Message/Frame convenience overload가 finally 대신 완료 시점에 release한다. 그러면 비동기로 쓰는 exporter가 retain하지 않아도 된다.
- export가 동기 예외로 반환하지 못하면 그 자리에서 release한다. 해제는 어느 경로에서도 정확히 한 번이다.
- 현재 exporter 셋은 모두 자기 복사본을 만든다. STOMP는 프레임마다 getBytes, TCP는 채널마다 copy, Vert.x는 getBytes다. 넓힌 수명은 PR 3 §4.4에서 압력 대기 중 원본 payload 참조를 공유하기 위한 준비다.
- 재시도할 encoded frame은 소유 참조를 갖되, 쓰기 계층이 거부와 함께 소비한 Buffer를 재사용하지 않는다.
- 테스트는 완료 전 참조 유지와 완료 후 해제, 그리고 동기 예외 경로를 확인한다. 취소와 executor 거부는 cancel을 도입할 때로 미룬다.

PR 2는 반환 계약과 구현만 바꾼다. stage를 실제로 기다리는 호출자는 PR 3의 lease가 처음이며, 그때까지 FanoutDispatchChainHandler는 반환값을 쓰지 않는다. 실제 pressure 대기와 socket 완료 추적도 PR 3에서 연결하며, 그 전에는 기존 write 성공 단계가 terminal write 완료인 것처럼 문서화하지 않는다.

## 4. PR 3 — 실제 쓰기 완료와 큐 전달 상태 기계

### 4.1 ChannelWriteBuffer의 추적 가능한 entry

- 내부 Queue<Buffer>를 버퍼, 최초 길이, 소비 바이트, 완료 callback을 가진 WriteEntry 큐로 변경한다.
- 소비 바이트가 전체 길이에 도달하면 해당 entry의 written 완료를 알린다. socket이 일부만 쓰거나 0을 반환하면 미완료로 유지한다.
- close 시 미완료 entry를 종료한다. 소비 바이트 0이면 NOT_SENT, 일부 소비됐다면 UNKNOWN이다. OS에 전부 인계된 entry는 WRITTEN이며 애플리케이션 수신 보장은 아니다.
- public `writeAndFlush`의 기존 의미는 별도 주제로 일괄 바꾸지 않는다. 새 tracked-write 경로를 추가하고 안정성 runner와 dispatch 전달이 이를 사용한다.
- 쓰기 full 예외를 문자열로 판별하지 않는다. pressure, 단일 encoded frame 초과, closed, I/O failure를 typed 결과로 구분한다.

### 4.2 ready와 write의 연결

채널 소유 이벤트 루프에서 `WriteAttempt`를 처리한다. 결과는 STARTED, DEFERRED, REJECTED다. STARTED에는 전체 write 완료 future가 연결된다.

- 준비 확인과 write entry 접수를 같은 이벤트 루프 작업 안에서 수행한다.
- 공간이 부족하면 DEFERRED를 반환하고 재개 알림을 등록한다. 확인·등록·재확인을 같은 루프에서 수행해 lost wakeup을 막는다.
- writable 전환뿐 아니라 bytes 소비로 필요한 용량이 확보되는 경우에도 재시도 가능 여부를 검사한다. 현재 writable=true인 상태에서 frame이 남은 용량보다 큰 경우를 놓치지 않는다.
- 알림은 one-shot, 취소 가능하다. close는 대기자를 실패 완료하고 registration을 제거한다. 여러 큐가 한 연결을 공유하면 FIFO로 공정하게 재개한다.
- entry보다 큰 프레임이 영원히 대기하지 않도록 전체 encoded frame이 hard limit보다 크면 FRAME_TOO_LARGE로 즉시 실패한다.
- 서버 시작 시 허용 STOMP frame 크기와 WebSocket 인코딩 상한이 transport hard limit 안에 들어가는지 검증한다. 맞지 않는 설정은 시작 오류로 알리고, 개별 SEND의 확정 oversize는 수락 전에 거부한다. 현재 기본 write buffer 128KiB와 예제 max-frame-length 1MiB의 차이도 여기서 해소한다. 한도를 조용히 늘리지 않고 시험 설정에 명시한다.
- DEFERRED는 byte 전송을 시작하지 않았다는 계약이다. 일반 send의 실패처럼 연결을 닫지 않는다. 실제 I/O 오류는 연결 종료 및 UNKNOWN 분류를 유지한다.

### 4.3 TCP·WebSocket outbound 전파

- 추적 context를 outbound pipeline 끝까지 전달한다. 단순 raw write로 우회해서 WebSocket 프레이밍을 건너뛰지 않는다.
- 한 STOMP frame이 여러 transport buffer로 변환되면 모든 자식 write가 완료돼야 부모 WRITTEN을 완료한다.
- retry 가능 거부는 자식 buffer 접수 전 용량을 모두 확보했을 때만 판정한다. 일부 자식이 제출된 뒤 실패하면 전체 frame을 재시도하지 않는다.
- context 없는 기존 pipeline 호출은 정상 유지한다. TLS는 이번 동등 부하 기준의 대상은 아니지만 변경으로 TLS pipeline을 우회하거나 버퍼 소유권을 깨뜨리지 않도록 기존 회귀 테스트를 실행한다.

### 4.4 큐 lease와 회계

DispatcherQueue에 아래 개념을 도입하고, release를 동반하는 기존 dispatch 호출부를 전환한다.

```java
AdmissionResult tryEnqueue(Message message);
@Nullable QueueDeliveryLease claim();
void finish(QueueDeliveryLease lease);
```

- 큐 내부의 짧은 잠금으로 open/pause, enqueue, claim, 삭제 여부와 예약을 함께 보호한다. 잠금 안에서 exporter나 외부 callback을 호출하지 않는다.
- enqueue는 queuedBytes와 outstandingBytes를 증가시킨다. claim은 queued → inFlight로 이동할 뿐 outstanding을 줄이지 않는다.
- 큐당 lease는 최대 1개다. finish는 lease identity를 확인하고 한 번만 inFlight와 outstanding을 감소시킨다.
- PR 2의 export stage는 결과 값을 싣지 않으므로 finish는 lease만 받는다. 대상별 결과가 필요해지면 exporter 반환 타입과 finish를 같이 넓힌다.
- 기존 pendingBytes는 `queuedBytes + inFlightBytes`로 정의한다. getSize는 대기 건수이며 outstandingMessages와 inFlightMessages를 별도로 노출한다.
- 큐 bytes는 payload 기준의 논리 보존량이다. 프레임 인코딩·대상별 복사·socket buffer는 별도의 메모리를 사용하므로 이 값을 서버 실제 메모리 총량으로 표시하지 않는다. 인코딩은 대상 채널이 전송을 접수할 때 지연 수행하고, 압력 대기 중에는 원본 payload 참조를 공유해 복사본 누적을 피한다.
- byte 한도 외 메시지 수 상한도 둔다. 기본 큐 outstandingMessages는 65,536으로 하며 zero-byte 메시지의 무제한 적재를 방지한다. 한도 값은 명시적 설정으로 노출한다.
- pressure는 admission에만 적용하고 이미 수락한 메시지의 drain은 허용한다. manual pause는 새 claim도 막되 이미 시작한 전달은 완료시킨다.

### 4.5 QueuePump

기존 장기 poll loop를 큐 인스턴스별 `QueuePump`로 교체한다. 상태는 IDLE, SCHEDULED, RUNNING, WAITING, CLOSED다.

1. enqueue·resume·구독 추가·전달 완료 이벤트가 signal을 발생시킨다.
2. signal은 중복 예약을 합치고 pump를 한 번만 실행한다. callback 연쇄로 재귀 호출하지 않는다.
3. pump는 대상 구독이 없으면 claim하지 않고 대기한다. 구독 추가 이벤트가 다시 깨운다. 메모리 한도에 도달하면 이후 발행은 거부된다.
4. 대상이 있으면 lease 하나와 구독 snapshot을 얻고 exporter가 반환한 stage에 완료 처리를 등록한다. stage 완료가 lease를 놓을 시점이다.
5. 일부 대상이 pressure로 대기하면 pump는 WAITING이며 작업 스레드를 반납한다.
6. delivery가 끝나면 lease를 finish하고 다음 drain을 예약한다.

현재 poll loop는 `queue.dispatch(1, TimeUnit.SECONDS)`의 주기적 반환에 종료를 의존한다. `Consumer.task()`가 CompletableFuture라 `cancel(true)`가 실행 중인 스레드를 인터럽트하지 않고, `queue.close()`도 producer만 깨우기 때문이다. 블로킹 `dispatch()`로 바꾸면 게이트웨이 close가 `awaitTermination` 60초를 모두 소모한 뒤 shutdownNow의 인터럽트로만 끝나고, 빈 큐를 삭제하면 그 consumer 스레드가 영구히 남는다. pump는 폴링과 블로킹 모두 없애 이 의존을 제거한다.

queue lock 안에서 idle 표시와 마지막 작업 유무 확인을 조율해 enqueue 직후 wakeup이 사라지지 않도록 한다. pump에는 큐 인스턴스를 저장해 삭제 후 같은 group/destination으로 생성된 큐를 이전 callback이 건드리지 못하게 한다.

제어 이벤트는 메시지마다 무한히 쌓지 않는다. 큐별 ready flag와 gateway의 하나의 wakeup 신호로 합치고, bounded admission executor와 별도 dispatcher control 실행 흐름에서 처리한다. control 흐름은 I/O 대기 없이 준비된 큐를 한 번씩 공정하게 진행한다. 스케줄링 종료·거부를 성공 수락 후 조용히 무시하지 않는다.

### 4.6 관리·연결 생명주기

- non-force delete는 queued와 in-flight를 모두 확인한다. 비어 있음 확인과 close 전환을 큐 lock 안에서 수행해 확인 직후 enqueue 경합을 차단한다.
- force delete는 queued를 명시적 취소하고 진행 delivery를 취소한다. 이미 제출된 write는 완료/종료까지 추적한다. registry에서 사라져도 lease 정리가 끝날 때까지 내부 객체를 유지한다.
- purge는 아직 claim하지 않은 대기 메시지만 비운다. in-flight를 되돌렸다고 표시하지 않는다. 이 의미를 CLI·HTTP 문서와 테스트에 명시한다.
- unsubscribe·connection close 이벤트를 exporter 대기 대상에 연결한다. 이미 보낸 메시지는 회수하지 않으며, 미전송 대상은 CANCELLED/NOT_SENT로 종료한다.
- shutdown은 admission을 먼저 닫고 drain deadline까지 진행한다. deadline 이후 queued·waiter를 취소하고 outstanding을 정리한다. 네트워크에 이미 제출된 write는 연결 종료 결과로 처리한다.

## 5. PR 4 — bounded admission과 오류 계약

### 5.1 수락의 원자적 경계

`DispatchGateway.sparkDispatch`의 접수 결과를 `CompletionStage<AdmissionResult>`로 변경한다. 결과는 ACCEPTED 또는 사유가 있는 REJECTED이며, 전송 완료 future와 분리한다.

```text
실행 슬롯·byte permit 확보
→ 큐/프로토콜/heap 정책 및 사용자 admission hook 검증
→ 큐 lock: open·manual pause·용량 확인, 예약·enqueue, pump 신호 등록
→ ACCEPTED
```

- admission hook은 enqueue 전에 실행한다. 수락 후 실행되는 사용자 hook의 예외를 '미수락'으로 응답하지 않는다. 기존 handler chain의 확장 지점을 admission/delivery 단계로 명확히 분리한다.
- commit 이전 실패는 모든 임시 permit을 반환하고 메시지를 enqueue하지 않는다. commit 이후의 callback 오류는 delivery/운영 오류이며 REJECTED로 되돌리지 않는다.
- 제한은 try-acquire 방식으로 판정한다. 가상 스레드를 사용하더라도 실행 슬롯을 먼저 확보하며, 상한 없이 새 task를 만들지 않는다.
- admission permit 기본값: 실행+대기 1,024건, task가 참조하는 payload 합계 16MiB. 작업 종료 시 반환한다. 고정·가상 스레드 gateway 모두 같은 제한을 적용한다.
- 큐 pending 한도와 admission byte 한도는 단계가 다르다. 순간 중첩 계상은 허용하되 permit 소유자는 명확히 하나이며 누락·이중 반환을 금지한다.
- gateway와 core I/O 작업 스케줄러가 거부한 경우도 구분한다. I/O 작업이 제출되지 못한 메시지는 localNotSent로 분류하며 버퍼를 반환한다.

### 5.2 거부 사유와 STOMP 응답

거부 코드는 QUEUE_FULL, MESSAGE_TOO_LARGE, MANUALLY_PAUSED, QUEUE_CLOSED, EXECUTOR_FULL, HEAP_PRESSURE, SHUTTING_DOWN, UNSUPPORTED_TRANSPORT로 구분한다.

- ACCEPTED인 SEND에만 수락 RECEIPT를 보낸다. 수락 후 RECEIPT 전송 실패는 클라이언트 입장에서 UNKNOWN일 수 있으므로 자동 재전송하지 않는다.
- REJECTED이면 ERROR에 원래 receipt-id, `titan-error-code`, `titan-retryable`을 넣는다. 프로토콜 encoder가 extension header를 전달하도록 갱신한다.
- retryable=true는 QUEUE_FULL, EXECUTOR_FULL, HEAP_PRESSURE에만 적용한다. 이는 현재 요청이 미수락임을 뜻하며 다음 시도의 성공을 보장하지 않는다.
- ERROR의 tracked write를 완료한 뒤 연결을 닫는다. 느린 연결에서는 기존 연결 종료 제한 내에 종료하며, ERROR를 못 받은 요청은 클라이언트가 UNKNOWN으로 처리한다.
- 네이티브 클라이언트는 ERROR의 receipt-id를 pending 요청에 연결해 typed 거부 결과를 먼저 전달하고 이후 연결을 정리한다. 관련 없는 다른 pending 요청은 UNKNOWN으로 남긴다.
- 재시도 실험은 명시적 retryable 거부만 대상으로, 재연결 후 지수 backoff(100ms 시작, 최대 2초, jitter, ID당 최대 3회)와 전체 deadline을 적용한다. 원본 ID와 attempt 번호를 분리해 중복을 관측한다. 기본 부하에서는 비활성이다.

## 6. PR 5 — 관측·설정·성공 판정

- 큐 snapshot: queuedBytes, inFlightBytes, pendingBytes, queuedMessages, inFlightMessages, accepted, rejectedByReason, writtenTargets, cancelledTargets, failedNotSentTargets, unknownTargets, pressureWaitCount/totalNanos/maxNanos.
- gateway snapshot: admissionActive, admissionQueued, admissionPendingBytes, rejectedByReason. gauge와 누적 counter를 구분한다.
- channel snapshot: 실제 pending bytes, nonWritable, ready 전환, tracked write 완료/실패. 클라이언트의 accepted와 서버의 written을 같은 의미로 표시하지 않는다.
- JVM 측정: heap, GC 횟수·시간, 스레드 수. 1초 간격으로 수집하고 측정 종료 후 drain 관찰 구간도 저장한다.
- JMX → collector → Java snapshot → HTTP → Go model·표시·테스트를 함께 갱신한다. 누락 필드를 성공적인 0으로 보정하지 않는다.
- queue 생성의 byte/message 한도, resume 한도와 admission 작업/byte 한도를 설정·runtime 출력에 포함한다. 기존 최상위 heap flow-control 스위치로 hard limit을 해제하지 않는다.
- 모든 조회 값이 완벽한 동시 snapshot이라고 가정하지 않는다. 정확한 보존 불변식은 큐 lock 안에서 검사하고 운영 지표는 시점 차이를 허용하는 관측값이다.
- 정상 부하 통과는 receipt 모드의 accepted=received=requested, rejected=unknown=duplicates=contradiction=0과 종료 정상이다. write 모드는 별도 수신 검증 결과이며 수락 확인 기준을 대체하지 않는다.

직접 STOMP 경로는 기존 best-effort 동작과 비교하기 위한 대상이다. 0.9.0의 큐 기반 보존 보장은 TCP·WebSocket 모두 dispatch 경로에서 제공한다. direct 결과를 dispatch 안정성 성공으로 합산하지 않는다. 릴리즈 예제와 기본 안정성 fixture는 dispatch 경로를 명시한다.

## 8. 실험·출시 기록

- 상위 계획의 1만/5만/10만 × 프로듀서 1/4/8/16 × TCP/WS × 3회 행렬을 receipt 모드의 정식 판정으로 실행한다. write 모드는 같은 조건의 수정 전후 비교를 별도로 수행한다.
- 기본 실험 payload 1KiB, 워밍업 1,000, deadline 120초. 기준 서버의 기존 30초 실험은 별도 결과로 보존한다.
- 과부하 fixture는 큐 64KiB/resume 48KiB로 낮추고 수신을 제어해 일부 수락·후속 거부를 만든다. 정상 부하 결과에 혼합하지 않는다.
- 수신 일시 정지는 테스트 장치로 구현한다. 재개 후 수락 ID 전량 수신, 중복 0, pending 0, 새 발행 성공을 확인한다.
- 하나의 느린 큐와 정상 큐를 함께 실행해 정상 큐가 멈추지 않는지 확인한다. 전역 admission 한도까지 포화시킨 실험은 전역 과부하로 별도 분류한다.
- 30분 지속 부하에서는 처리량·지연뿐 아니라 반복 후 pending, waiter, lease, 작업, 참조가 누적되지 않는지 확인한다. 순간 heap 상승만으로 누수를 판정하지 않는다.
- 신규 hard limit 때문에 거부된 실행을 무리하게 한도만 높여 정상 통과시키지 않는다. 정상 부하 envelope와 과부하 결과를 분리해 기록한다.
- 결과 문서에는 실행 여부, 조건, 재현된 실패, 수정 원인, 재실행 결과와 남은 한계를 기록한다. 아직 실행하지 않은 값은 작성하지 않는다.

현재 문서는 구현 설계 산출물이다. 코드 변경·10만 건 부하 실행·성능 수치 측정·PR 생성은 포함하지 않는다.
